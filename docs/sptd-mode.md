# sptd mode for the demo scripts (development only)

sptd mode runs the demos on a Kubernetes cluster whose nodes use the SCONE SPTD kernel:
each demo first runs as a native app, then as a confidential app made of SCONE Process TDs.
This is a development path. CAS is bypassed and envcas attestation is off. Values compiled
into a bundle are readable test data, not protected secrets. Never use it with real secrets.

## Using it

```bash
./scripts/prepare-example-ci.sh --mode sptd
export PATH="$PWD/scripts/sptd/bin:$PATH"
./scripts/run-all-scripts.sh --continue-on-failure
```

`prepare-example-ci.sh --mode sptd` sets `TEE_TYPE=sptd` and `SCONE_ENCLAVE='false'` in every
`Values.yaml`, as `sgx` and `cvm` do. `--mode sgx|cvm` and `--namespace` are unchanged.

## How it works

Every demo README (extracted into `scripts/<demo>.sh`) builds and pushes the native image,
deploys and checks the native app, deletes it, tries CAS attestation (it already falls back
to "CAS attestation skipped" when no CAS answers), runs `scone-td-build apply -f scone.yaml`
and deploys the resulting `output-manifest`. sptd mode changes only the `scone-td-build`
step, so the READMEs and the generated scripts stay as they are.

`scripts/sptd/bin/scone-td-build` is a dispatcher. Unless `TEE_TYPE=sptd`, it runs the real
`scone-td-build` unchanged. With `TEE_TYPE=sptd`, `scripts/sptd/td-build-sptd.py` handles
`apply -f scone.yaml`. For each container whose image is registered in the `Register`
documents, it:

1. takes the source image: a demo's sptd variant image if one exists
   (`scripts/sptd/images/<demo>/Dockerfile`, built with the demo directory as context, or
   `<demo>/Dockerfile.sptd`), otherwise the pushed native image;
2. writes a Pod, the referenced ConfigMap/Secret snapshots, a launch-contract policy
   (`scripts/sptd/policies/<demo>.json` or `generic.json`) and an onboarding request;
3. runs the offline onboarding of sptd-hello-container-dev
   (`scone-dev-onboard/onboard.py`): an EROFS + dm-verity root filesystem from the image, a
   launch contract, a sealed launcher, a signed per-image profile and a signed profile
   registry;
4. writes the `output-manifest` with the onboarded image, RuntimeClass `scone-dev`,
   `hostNetwork: true`, `nodeName` (`SPTD_NODE_NAME`) and a `node.kubernetes.io/not-ready`
   toleration.

Single-container workloads stay Jobs or Deployments and need only the signed registry on the
node. A workload with several containers, init containers or a memory emptyDir becomes a bare
Pod with one signed Pod plan (`scone-dev-onboard/pod_plan.py`). The node must have the
bundles, the registry and any plans installed before the confidential manifests are applied.

A demo can ship a variant for sptd mode only: `<stem>.sptd.template.yaml` next to a manifest
template (rendered with `tplenv`), a source image under `scripts/sptd/images/<demo>/`, endpoint
intent in `scripts/sptd/policies/<demo>.endpoints.json`, and per-workload overrides in
`scripts/sptd/policies/<demo>.overrides.json`.

## Environment

| Variable | Meaning |
| --- | --- |
| `SPTD_ROUTE` | `a8` (default) or `dev-prepare` (scone-sptd-build `sptd-dev-prepare`, static binaries only) |
| `SPTD_ONBOARD`, `SPTD_A8_TOOLS` | path to `onboard.py` and its `tools` object |
| `SPTD_DEV_SIGNING_KEY`, `SPTD_DEV_ROOT_PIN` | the development signing key and its root pin (`sha256:<hex>`); never generated by the script |
| `SPTD_NODE_NAME` | node for `nodeName` |
| `SPTD_SOURCE_LAYOUTS` | JSON map `{image: OCI layout or oci-archive}`; with `SPTD_A8_OFFLINE=true`, nothing is pulled or built |
| `SPTD_A8_COMPILER_FEATURES`, `SPTD_A8_MEMORY_ASSEMBLY` | compiler features and memory assembly for the baked-volume and memory routes |
| `SPTD_DEV_LINT` | optional scone-sptd-build `sptd-dev-lint` pre-flight |
| `SPTD_WORK_DIR` | work directory (default `.sptd-work`) |

The node's envcas reads the root pin as bare hex (`SCONE_SPTD_N3_ROOT_PIN`), without the
`sha256:` prefix. The script writes no node configuration.

## Pinned rust-envcas revision

sptd mode is pinned to rust-envcas `main` at `f69a0a61914d8ff53fb168c9b800c8e65a2c5c5b`.
Build the `compiler` and `envcas_source` entries of `SPTD_A8_TOOLS` from that commit. It
contains:

- `scone-td-dev-compile` running Cmd for Cmd-only images (rust-envcas #46);
- the NON_RELEASE baked ConfigMap/Secret volumes behind the default-off
  `nonrelease-dev-baked-volumes` feature (rust-envcas #47; list it in
  `SPTD_A8_COMPILER_FEATURES` when the compiler is built with it);
- measured script executables for CPython (rust-envcas #49).

Bundles onboarded with an earlier envcas build bind that build's digests and must be onboarded
and signed again.

## Temporary: baked ConfigMap and Secret files

Until CAS delivers configuration files to a TD, some demos bake their ConfigMap and Secret
files into the sealed launcher (rust-envcas `scone-td-dev-compile` built with
`nonrelease-dev-baked-volumes`). The files appear in the TD as read-only descriptor files
descriptors 100, 101, … numbered by volume name, then path, and opened as
`/proc/self/fd/N` (not the `/dev/fd/N` symlink). The script computes the
numbering before onboarding and refuses a bundle whose `baked-volumes.json` differs.

- flask-redis (redis): `redis.conf` is descriptor 100, the TLS files 101-103; the baked
  `redis.conf` points at them, and redis starts as `redis-server /proc/self/fd/100`. `/data`
  is a memory emptyDir.
- go-args-env-file, java-args-env-file: each ships a `manifest.sptd.template.yaml` that
  mounts the ConfigMap and Secret as whole volumes outside `/config` instead of `subPath`
  mounts (java-args-env-file also runs the native-image binary). The sptd source image links
  `/config/configs.yaml` to `/proc/self/fd/100` and `/config/secrets` to `/proc/self/fd/101`.
- hello-world, image-signing and network-policy build small sptd source images from
  `scripts/sptd/images/` (static or distroless, uid 65532). hello-world and image-signing share
  one Dockerfile; `--build-arg DEMO=` gives them different config digests.
- configmap: the Job runs two readers of one image with different ConfigMap items at `/config`.
  A signed Pod plan can't carry two roles of one image, so sptd mode builds one source image per
  reader (`scripts/sptd/images/configmap`, `--build-arg READER=1|2`) and uses
  `manifests/manifest.sptd.template.yaml` and `manifests/scone.sptd.template.yaml` (one Register
  per image; set `CONFIGMAP_READER_1_IMAGE` and `CONFIGMAP_READER_2_IMAGE`). Each image ships
  `/config` as a directory of symlinks to that reader's descriptors, so `folder-reader` still
  lists and reads the folder.
- web-server: the `game-demo` ConfigMap at `/config` is baked; the sptd source image links each
  `/config/<key>` to its descriptor, and the dispatcher checks the links (`imageLinks` in the
  overrides). `MY_POD_IP` is left out in sptd mode: the server listens on `0.0.0.0` and only
  echoes that variable, so `/env/MY_POD_IP` answers 404.

Baked values are fixed at build time. This whole mechanism, including those symlinks, is
removed once CAS delivers the files.

## Current limits

- Python demos (flask-redis and flask-redis-netshield flask-api, software-updates v1/v2) are
  set up as measured CPython script targets: `policies/python-script.json` (`-I -B`) or
  `python-script-stdlib.json` (`-I -B -S`) pins the real interpreter
  `/usr/local/bin/python3.11` with `python` and `python3` as aliases and denies the
  loader, OpenSSL, glibc and `PYTHON*` environment prefixes; the overrides make the absolute
  script (`/app/app.py`, `/app/print_env.py`) the command. `scone-td-dev-compile` from the
  pinned rust-envcas main accepts `script` executables (rust-envcas #49); the profile emitter
  of `scone-dev-onboard` does so only with sptd-hello-container-dev #101, which is not merged
  yet.
  flask-redis's flask-api also needs its `/tls` Secret baked. nfs-shared-volume is not covered.
- Java demos (java-args-env-file, pet-clinic) run as GraalVM native-image binaries in sptd
  mode, built from `scripts/sptd/images/`; no JVM runs in a TD.
- ConfigMap and Secret volume mounts are refused unless baked (above). PVCs and the Downward
  API are not supported.
- Confidential Pods use the host network, so Service names and several replicas on one port
  don't work yet, and a native app must be deleted before its confidential twin starts.
- `kubectl port-forward` on a host-network Pod reaches the node's localhost.
